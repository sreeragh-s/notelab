# Discovery and initial setup

[Contracts](../../../apps/server/src/features/instance/contracts.ts) define protocol version, instance identity, origins, server/minimum desktop versions and desktop authorization endpoints. They import no runtime or persistence implementation. [Discovery](../../../apps/server/src/features/instance/discovery.ts) resolves canonical configured origins and validates versions before loading identity; edition options add only the edition ID and declared capabilities.

[Instance settings](../../../apps/server/src/features/instance/instance-settings.ts) owns the primary settings row and database environment scope. Initialization reads existing identity, inserts with conflict-ignore, then re-reads the persisted winner. The production repository and controlled test repository use the same interface; changing the display-name environment setting does not overwrite an existing identity. [Desktop version rules](../../../apps/server/src/features/instance/desktop-version.ts) compare protocol and semantic versions, including prerelease ordering, without importing a database or web UI.

The [setup screen](../../../apps/web/src/features/auth/screens/setup.tsx) owns pending/error/completion presentation. Its [bootstrap operation](../../../apps/web/src/features/auth/setup/bootstrap-instance.ts) normalizes owner/workspace fields, submits the bootstrap token only in the request header, marks bootstrap complete, then signs in with email/password. The screen redirects only after sign-in succeeds. If sign-in fails after bootstrap, the screen offers manual login rather than suggesting that initialization never happened. No token is written to browser storage or a URL.

Server [registration](../../../apps/server/src/features/instance/registration.ts) owns bootstrap serialization, initial owner/workspace creation and subsequent registration policy. Bootstrap and owner checks remain authoritative on the server. Discovery publishes OAuth authorization, token, revocation, introspection and JWKS endpoints alongside desktop authorization. It ensures the official Web Clipper client exists inside the database environment; concurrent inserts tolerate the client-ID conflict. Discovery is public identity/configuration data, not a source of bootstrap credentials. Read the [self-hosting guide](../../setup/self-hosting.md) for operational setup.

[Instance tests](../../../apps/server/src/features/instance/service.test.ts) exercise discovery, version rejection and concurrent identity initialization with a controlled repository. [Bootstrap tests](../../../apps/web/test/features/auth/bootstrap-instance.test.mjs) exercise the real operation with controlled HTTP calls, including initialization failure and sign-in failure after completion. These tests do not initialize a real database or send authentication email.
