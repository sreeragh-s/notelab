# Upgrades, reinstall and deletion

The application bundle and local workspace have independent lifetimes. Release data lives under macOS Application Support for `com.zilobase`, in `local`; debug data uses `local-debug`. Deleting the `.app` in Finder leaves this directory intact. Reinstalling and selecting On this Mac rediscovers the installation and creates a fresh local session without Keychain recovery or online login. Third-party uninstall cleaners can also remove Application Support; keep an exported backup separately.

PostgreSQL stays on major 17. Startup checks the database migration journal against the bundled migration hashes before applying migrations or starting the API. Divergent or newer histories are rejected. Existing installations receive a verified `backups/pre-upgrade.zilobackup` before pending schema migrations; failure to back up blocks the upgrade. Successful migration records schema metadata separately from the database major version. Failed migration data stays in place and can be restored from the pre-upgrade archive.

Delete local workspace data is a separate settings action requiring the exact text `DELETE LOCAL WORKSPACE`. It checks installation identity and the canonical directory, stops capture and the runtime, retains the exclusive installation lock, and refuses deletion if a PostgreSQL PID file remains. It deletes the selected installation including its internal backups. Exports outside that directory, sibling restore recovery copies and independently installed AI services remain. A deletion marker returns startup to mode selection instead of silently creating a replacement or connecting to Cloud.

The backend receives native parent EOF on ordinary exit. A separate bundled watchdog watches the backend pipe and requests bounded PostgreSQL shutdown even if the backend is killed. Restart additionally verifies the exact postmaster command and data directory before attempting orphan cleanup; unfamiliar processes require manual recovery.

For a future PostgreSQL major upgrade: ship both verified majors and the new restore tools in a separate release; take an independently verified logical backup; initialize the new major in staging with new credentials; restore and migrate there; validate objects and representative queries; then activate by directory swap while retaining the old installation. Never point a newer major directly at the old data directory. Downgrading requires restoring a compatible backup.

Remaining release tests include Finder deletion/reinstall on clean machines, native typed deletion, low-disk migration failure, forced native-process termination during maintenance, and multi-window coordination. The internal feature flag remains required until the release acceptance matrix is complete.
